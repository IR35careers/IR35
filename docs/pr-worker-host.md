# Docker and loopback update boundary

## What and why

Connect the previously prepared transaction journal to real bounded Docker/cosign subprocesses, owner-private configuration files and authenticated loopback HTTP. The default adapter uses actual commands/fetch/WorkerFiles, not a simulated deployment. No executable entry point, timer or automatic enablement is added yet.

This is stacked on unmerged PR #36 (journal core), not permission to merge it or deploy. New draft PRs remain human-reviewed; PR #37 separately installs the bot workflow/main code-owner policy. No automatic merge/release authority remains.

Docker inspection requests only selected container ID, immutable image/image ID, state, exact Compose ownership/boot labels and localhost binding. It never requests `.Config.Env`, full inspection, Compose's resolved config or a secret file dump. Only one exact owned service is allowed. Docker generation/configuration are checked around the health request; slow rechecks cannot freshen an old health timestamp. Health is bounded/validated and unavailable/mismatched replies cannot become healthy journal proof. Drain/resume uses the existing real HMAC protocol and treats 202 as acknowledgement, not completion.

Every Docker command pins --host unix:///var/run/docker.sock, not just a sanitized environment: a saved currentContext could otherwise select a remote daemon. Invalid/non-integer/backwards clocks stop before mutation. A failed repeat signature check clears its earlier cached replacement authorisation.

Before pulling, successful cosign verification must match the exact workflow identity/issuer/annotations and immutable revision callback. After pulling, actual Docker architecture, OS, digest, revision and image ID are checked. Replacement requires those prepared signed source/target artifacts, a matching durable journal intent, a fresh unchanged observation and an original unexpired health deadline. Only the UUID/label override and image line are written; raw worker secrets, runner and acceptance values are not rewritten. Compose is restricted to the worker, detached/no-build/no-dependencies/no-pull. It never prunes images or automatically repeats an uncertain Compose command.

Rollback is permitted only before a durable resume decision and for the exact owned candidate boot generation, or positively empty Docker inventory after failed creation. Unready startup DB/browser health is not proof of readiness, but an owned never-resumed boot-paused candidate may be replaced with the already verified previous image under a different paused boot UUID. Rollback must subsequently pass full fresh readiness before resume; a reported idle/resuming/active candidate, foreign generation or changed config refuses replacement. A late candidate from an unknown daemon acknowledgement remains boot-paused, not authorised to claim jobs.

## Tests and limitations

28 focused tests pass. Most command/config tests inject bounded disposable responses and do not prove an actual Docker deployment. One test sends actual HTTP requests through a loopback server running the real maintenance HMAC handler, proving authenticated drain/resume and conflict rejection without any consumer or employer request. Tests cover wrong signatures/tags/architecture/revision/image IDs, changed container/configuration/flags, slow/stale/invalid/backwards clocks and delayed credential reads, failed repeat verification, unavailable/malformed/oversized health, past deadlines, preserved settings, positive pre-resume rollback, missing candidate, wrong/resumed generation and lost Compose acknowledgement. No new skip, tolerance or security exception.

Native ARM CI additionally prepares a real Docker selected-field/socket/local-image rejection probe. It uses a deliberately nonexistent saved Docker context as a negative control, checks exact real ID/image/labels/localhost mapping without returning a canary environment value, then proves a local/mutable image cannot become eligible host health evidence. It does not substitute a fictional GHCR digest into actual Docker output, run a queue consumer or claim signed provenance. Its real Linux result is pending CI; there is no local Docker Desktop result. Actual signed-image replacement/rollback remains a later gated staging requirement.

The first local pass found Windows path joining in the Linux command adapter; fixed the code to use explicit POSIX paths, retaining exact command assertions. The first combined release check caught two unused fixture arguments; fixed the fixture, not the zero-warning lint gate. Full local verification passes **946 unit tests/139 files + 199 legacy checks**, strict types, zero-warning lint and source/history scan (712 tracked files). Audit retains only the two existing exact exceptions until 29 October; no new waiver. Native probe exits 1 on this Windows/non-Actions machine before invoking Docker, as required; this is guard evidence, not a Docker result. No UI/screenshots apply.

Still required: serial host interpreter/reconciliation, same shared flock for updater/operator edits, credential/bootstrap setup, anti-replay/main ancestry policy, persistent journal binding, bounded polling with original deadlines, actual Linux/Docker recovery matrix, installation and five-minute timer. A caller cannot treat arbitrary injected test objects as verified physical state or replace the actual signature/tag gates with mocks on the host. This module alone is not a working automatic updater.
