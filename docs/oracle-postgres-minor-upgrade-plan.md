## 2. Read-only compatibility review before rehearsal

Use a new write-once evidence directory, the recorded snapshot and a separately owned disposable staging copy. Never change production to resolve a finding. Review every intervening migration section: [17.7](https://www.postgresql.org/docs/17/release-17-7.html), [17.8](https://www.postgresql.org/docs/17/release-17-8.html), [17.9](https://www.postgresql.org/docs/17/release-17-9.html), [17.10](https://www.postgresql.org/docs/17/release-17-10.html) and [17.11](https://www.postgresql.org/docs/17/release-17-11.html). Direct same-major replacement does not justify ignoring cumulative changes.

- Inventory every database's installed extensions, versions, owners, members, libraries, preload settings, collation/encoding and custom operators; do not infer absence from one database. The existing five-version baseline is `pg_stat_statements 1.11`, `pgcrypto 1.3`, `plpgsql 1.0`, `supabase_vault 0.3.1`, `uuid-ossp 1.1`. Reconfirm against the snapshot and exact candidate. Require matching installed versions and usable compatible binaries. No automatic `ALTER EXTENSION UPDATE`, default-version substitution, dropped extension, grant change or catalog repair.
- Inventory logical replication publications, slots and plugins, including Realtime. PostgreSQL 17.11 introduces `output_plugin_libraries`; the default includes `pgoutput` and `test_decoding`, not every third-party plugin. Allow only observed required trusted plugins after reviewing candidate availability. Do not drop a slot, erase a WAL position or broaden replication privileges to make startup pass. Prove Realtime reconnect and actual disposable-fixture CDC after the update. [17.11 logical-decoding change](https://www.postgresql.org/docs/17/release-17-11.html).
- Inspect `ltree`/`btree_gist` index applicability and custom selectivity estimators using the upstream detection guidance. Check whether application or extension routines use legacy-cipher `pgcrypto` PGP operations; its presence alone does not prove affected data exists. Supabase identifies possible reindexing, legacy PGP and custom-operator restore issues in this update. Record applicable/not-applicable with evidence, not an assumption. [Supabase's 17.11 compatibility notice](https://supabase.com/changelog/postgres-15-19-17-11-breaking-changes).
- **Stop for an applicable data-cleanup requirement.** Re-encryption changes bytes and cannot be hidden inside this zero-loss migration; disabling a cipher check or rewriting data is not authorized. Required reindexing must be separately scoped, rehearsed and compared without changing logical data. Do not copy upstream workarounds that skip COPY records, alter functions/operators, omit ACLs or waive schema parity.
- Compare locale, libc/ICU/OpenSSL and image UID/GID/config/data paths. Preserve `pg_hba.conf` ordering and the approved queue-database-only denials. No new public listener, admin access, app-role elevation, password, JWT or key changes. Report extension or platform deltas before proceeding; the three previously approved extension-owner exceptions do not authorize any new difference.

## 5. Rollback and dependent-component boundary

Core PostgreSQL minor releases share the same storage format, but that is **not a guarantee** that a Supabase image's bootstrap SQL, bundled extensions or dependent-service migrations are reversible. Keep the exact prior 17.6 digest plus the verified, quiesced pre-update data/config copy and encrypted full restore set. [PostgreSQL same-major compatibility](https://www.postgresql.org/docs/17/upgrading.html).

On a fixture failure: retain evidence, keep writers stopped, cleanly stop only the owned candidate, and restore the untouched pre-update copy onto a new owned recovery destination with the exact prior pin/config. Never start two servers on one data path, overwrite the rollback copy, or merely point the old image at a directory changed by unreviewed SQL/extension updates. Verify every gate above before reopening even fixture writes. A logical restore fallback must itself have been tested on the exact old image; do not assume new dump/extension output will restore unchanged.

Once writes resume after an eventual approved upgrade, reverting to the pre-upgrade snapshot alone would lose data. Freeze, preserve every later row/object change and use only a separately rehearsed zero-loss recovery path; otherwise stop and keep writes frozen. Do not turn a container rollback into a production reverse-sync.

The existing whole-stack rollback remains independent: within 48 hours of approved cutover, freeze/drain, execute the tested reverse-sync and full PASS verification, then the owner restores DNS to Vercel; after 48 hours roll forward only. Vercel/Supabase cloud remain intact for 14 days and are never used as an upgrade test target. Neither the minor-update checklist nor its eventual staging PASS supplies YES CUTOVER, DNS approval or real runner acceptance.
