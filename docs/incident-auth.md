## Verified gaps

1. No `src/app/auth/callback` route/page exists. An unauthenticated HEAD to `https://www.ir35careers.com/auth/callback` returned **404**. No token or email was sent by this check.
2. `signUpWithPassword` in `src/lib/auth-context.tsx` sets `emailRedirectTo` to the browser origin plus the final destination, not the required canonical dedicated callback. Password reset likewise derives its origin from the browser. The Google helper independently canonicalizes origins but still targets the final page. Keep the admin Google path separate when implementing a customer callback.
3. `SignInForm` has no confirmation-resend action or dedicated expired-confirmation recovery state. It shows a Check your inbox screen after signup. An expired/consumed link must get an explicit, safe recovery route without exposing token/error query details as trusted content.
4. The submission and Auto Apply handlers authenticate users, but contain no explicit `email_confirmed_at` gate. Supabase's own login policies are not a substitute for the brief's server-side requirement before applying. A confirmed combined/phone timestamp or user-editable metadata must not be treated as verified email.
5. `WorkspacePage` redirects logged-out users with only `window.location.pathname`, losing the query/hash. `SignInForm` shows generic account copy, not the saved job/company apply intent. Existing `resolvePostAuthPath` protects allowed internal destinations and must remain the redirect boundary; do not trust query-supplied employer/title text as job facts.
6. `/profile#apply-settings` sets the settings tab in a hash effect, but `firstTimeResumeRequired` still returns the CV-upload screen regardless of that tab. This explains the observed deep-link override for an account without a primary CV.

The reported `otp_expired` is **not attributed solely to a host redirect**: link expiry, prior consumption and email security scanning remain unproven possibilities. Do not log or reuse a customer's confirmation link to diagnose it.

## Code follow-up — canonical callback and application context

- `auth-routing.ts` supplies one canonical www callback builder. Signup, explicit confirmation resend and password reset use it, preserving the allowlisted destination (including `/account/reset`, saved application query and approval anchor). Customer Google sign-in uses the callback; admin Google sign-in still returns to the admin root. GitHub identity/import remains separate.
- `/auth/callback` is a real dynamic, noindex/no-store page with a no-referrer policy and fixed recovery copy. It waits for the SDK's cached initialization then verifies the user with `getUser`; it does **not** replay a one-use exchange. The actual installed SDK is tested against isolated HTTP fixtures for implicit tokens and a configured PKCE flow; the production client retains its existing implicit flow. Tokens/provider details are removed from history, not displayed as trusted text. The operation is bounded.
- Expired, invalid and unconfirmed callbacks offer explicit resend. Signup and `email_not_confirmed` password errors use the same recovery UI. No automatic email request on link opening, account-enumerating success claim or fake preview success; click/cooldown protection supplements Supabase's rate limit. Account/callback routes are excluded from application analytics; nonce CSP remains intact.
- Manual submission and Auto Apply require provider-returned `email` and valid `email_confirmed_at` **before packet/database/queue access**, including signed internal resumes and scheduled Auto Apply. Phone/combined timestamps and user-editable metadata do not count. Rejections are 403 `EMAIL_CONFIRMATION_REQUIRED` with recovery action. Tenant/lifecycle/approval/receipt checks still run for confirmed users; confirmation is not submission approval. Workspace recovery retains the current page.
- The worker rechecks provider confirmation at claim time, protecting already-queued work or an identity changed after enqueue. An unconfirmed/missing identity yields the existing needs-user preflight outcome and a confirmation recovery action, **without any CV/portal/browser payload or browser execution**. Confirmed users still pass through the original approval gates. This is distinct from the entry-point zero-database-access rejection above: a scoped service claim/heartbeat necessarily precedes reading the queued user's identity.
- Logged-out workspace sign-in preserves path/query/hash. Contextual sign-in loads the actual public job by validated UUID, validates/matches the response and ignores query-supplied employer/title text. Unavailable listings use an honest fallback. `/profile#apply-settings` is no longer masked by the first-CV upload return.
